## ADR-008 — Better Auth with PostgreSQL sessions

Status: Accepted

Authentication uses Better Auth with Fastify and the official Drizzle adapter.

PostgreSQL stores users, credentials, and sessions. Session cookies are HttpOnly and managed by Better Auth. The application does not implement custom password hashing, session cryptography, token rotation, or cookie signing.

Better Auth's `user` table is the canonical user identity. Domain tables will reference that user ID. User, session, account, and verification IDs are UUIDs generated by PostgreSQL through Better Auth's `generateId: "uuid"` setting.

## ADR-009 — Paper account as the financial identity

Status: Accepted

The first financial-domain entity is `paper_account`. Better Auth's `account` table remains credentials/OAuth storage and is not a trading account.

Identity:

- `paper_account.id` is a PostgreSQL-generated UUID
- `paper_account.user_id` is a unique foreign key to Better Auth `user.id`
- `ON DELETE RESTRICT` so deleting a user cannot silently destroy financial identity

Collateral:

- `currency` is persisted as `text` with `CHECK (currency = 'USDT')`
- this is not a multi-currency wallet model

Balance:

- `balance` is a current cash projection stored as `NUMERIC(38,18)`
- Drizzle reads and writes it as a `string`
- newly created Phase 3 accounts start at `0`
- Phase 3 does not credit 1,000 USDT

Status is `ACTIVE` or `SUSPENDED` (`text` + `CHECK`). `last_faucet_claim_at` is nullable and unused until the faucet phase. There is no `version` column; later financial writes will use PostgreSQL row locks.

### Lazy provisioning

Phase 3 does not create a paper account during Better Auth signup. An authenticated user may temporarily have zero paper accounts.

`ensurePaperAccount(executor, userId)` inserts a zero-balance row with `ON CONFLICT (user_id) DO NOTHING` and returns the created or existing row. Authenticated `GET /api/account` calls this primitive.

Phase 3 guarantees:

- a user can never have more than one paper account (`UNIQUE(user_id)`)
- after `ensurePaperAccount` succeeds, exactly one account exists for that user
- repeated or concurrent ensure calls return/use the same logical account

Phase 3 does not guarantee that every auth user already has a paper account before ensure runs.

### Phase 4 boundary

Phase 4 can make paper-account provisioning, signup allocation, ledger, funding event, and balance projection atomic with each other inside one financial transaction.

Atomicity between Better Auth's already-committed user creation and that financial transaction is an unresolved architecture decision. It is not solved in Phase 3 and is not assumed to be solved automatically in Phase 4.
